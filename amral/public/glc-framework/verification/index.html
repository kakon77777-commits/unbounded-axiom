工程驗證軌跡:七角色對抗式驗證,v0.2 → v0.2.6

這是獨立於本頁其他內容的另一條研究線:2026-08-09 起,7 個 AI 角色分工,對一個跟「P/NP 動態四層閉合框架」相關的工程候選(candidate)反覆做對抗式驗證——AI-1 統籌裁定、AI-2 紅隊唯讀核對凍結證據、AI-3 形式接口審查(含 Lean 4 形式化)、AI-4 建構候選本身、AI-5 完全不信任候選自帶的驗證器、獨立重寫邏輯核對,另有 AI-6、AI-7 兩位獨立學者做傳統複雜度理論的盲讀評估。從 v0.2 到 v0.2.6 共 7 個版本、至少 12 個互不相同的 blocker 被發現又修復,看起來是真的逐輪加深審查、在修好一個洞之後於下一層發現新的洞,不是同一問題卡住不動,也不是左手驗右手的重複蓋章。截至 v0.2.6:AI-1(統籌)與 AI-5(獨立重播)仍判定 FAIL;AI-2 的 PASS 範圍嚴格限定在既有凍結證據的一致性核對,明確排除獨立重驗與任何 P/NP 推論。兩位獨立學者的判斷更根本:即使這條工程驗證線全部轉綠,也不構成 P/NP 的任何結論。

CANDIDATE_UNPROMOTED / FAIL — 依 AI-1 統籌報告(v0.2.6),本頁其餘各角色報告作為並列證據,不代表整體已通過驗收。

五個工程角色 · v0.2.6 現況

「PASS」欄位是各角色自己嚴格界定的範圍,不是整體驗收結果——見下方各角色備註。

角色職掌v0.2.6 結果範圍備註

統籌		 核對各方 disposition 與 manifest 一致性,分歧時裁定 FAIL 2 個 blocker:CLOSURE-OPAQUE-LEAF-TERMINAL-01(採 AI-3 判定)+ ACCEPTANCE-PACKET-IMPORT-EDGE-COUNT-01(採 AI-5 判定)。文件自陳:「不發布 Board success、不建立 shared repo、不啟動下一版」。

AI-3

AI-5
獨立重播		 不信任候選自帶驗證器,完全獨立重寫邏輯核對 FAIL 216 項雜湊、31 條 import edge、112 個 evidence hash、1500 案例全部獨立重算通過,唯獨候選封裝內一份文件寫 29 條 import edge(其餘四個來源皆 31)導致整體 FAIL。v0.2.1 起從未給過乾淨 PASS。

v0.2.6 的兩個 blocker

CLOSURE-OPAQUE-LEAF-TERMINAL-01(AI-3)——候選的規範判斷圖裡,OpaqueLeaf 是 SupportedTraversal.child_dispatch 的一個目標分支,但沒有定義它該映射到 PASS/FAIL/UNKNOWN 哪一個終態。這不是假設性問題:AI-3 在凍結測資裡找到一條真的會走到這個分支的資料,而可執行的驗證程式在此把它當 PASS 繼續執行——是「規範圖」與「實際執行」之間的介面缺口,不是 admission bypass、正確性反例,或 P/NP 結論。這其實是修好上一輪(v0.2.5)的 CLOSURE-SUPPORTED-RELATION-RESULT-01 之後,判斷圖第一次真正走到下一節點,才第一次暴露出來的下一層缺口。

ACCEPTANCE-PACKET-IMPORT-EDGE-COUNT-01(AI-5)——候選封裝裡 CURRENT-v0.2.6-candidate.md 寫「29 條 local import edges」,但同一封裝內的 machine descriptor、官方 self-check、VALIDATION-REPORT-v0.2.6-candidate.md,以及 AI-5 自己獨立用 AST 重新算出的結果全部是 31 條。單純的文件計數不一致,不是正確性錯誤,但依流程規則仍構成 promotion blocker。

兩位獨立學者的判斷

AI-6(傳統複雜度理論學者)與 AI-7(跨範式橋接學者)跟上面的工程驗證線完全分開,各自做 blind review,互相未見對方初稿。

「這不是一份失敗的 P/NP 證明;它目前也不是 P/NP 證明。」——AI-6,首輪盲讀。第二輪覆審維持原判:研究綱領可以繼續、比第一輪成熟,但作為 P/NP characterization theorem 投稿,「至少是 major revision」;作為已證明 P=NP、P≠NP 或已建立新複雜度類的材料,「不成立」。
「不能把工程閉合升格成數學閉合。」——AI-7,跨範式橋接報告。第二輪逐條核對 AI-6 的判斷是否被後續工程與形式化進展推翻,結論是沒有:「每一項結果只可向上移動一層……不能由多個工程綠燈的數量直接跨到 P/NP conclusion。」

兩人都特別提醒:目前沒有任何已知複雜度障礙(relativization 等)被實際碰觸過;Lean 端雖然編譯乾淨,但 zeroDebt 這類引理可能被空洞代入而失去意義,不宜過度解讀「編譯成功」本身的份量;GLC 的「robust」語義目前只在單一 deterministic run 上測過,不等於已驗證一般容錯/非決定性語義。

版本軌跡

v0.2 到 v0.2.6 共 7 個版本標籤,至少 12 個互不相同命名的 blocker ID(PROV-DERIVE-01、REF-TYPE-01、CLOSURE-CLASS-01、CLOSURE-EDGE-SCOPE-01、ORACLE-DECL-FAMILY-01、CLOSURE-JUDGMENT-COMPLETENESS-01、ADVICE-DECL-LEDGER-01,加上 v0.2.5、v0.2.6 各自的新 blocker),無一重複命名。v0.2.3 曾一度標記 PASS,隨後被 ADDENDUM 更正為 FAIL。整體讀起來像是逐輪修掉舊缺口、審查深度也逐輪加深後再挖出新缺口的持續 hardening 過程,而不是同一缺陷反覆出現,也不是驗證方對工程方照單全收。
