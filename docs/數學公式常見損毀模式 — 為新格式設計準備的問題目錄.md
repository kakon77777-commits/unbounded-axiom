# 數學公式常見損毀模式 — 為新格式設計準備的問題目錄

給你設計專用格式用的問題清單。這裡只列「實際發生過、我修過」的案例，不列假設性的
邊角案例；每一類都盡量附上真實的損毀前/損毀後文字，方便你判斷新格式要在哪一個
環節堵住它。

跟 [`AI-Native 論文寫作規範`](AI-Native%20論文寫作規範%20—%20問答式節點與自洽定義區塊.md)
是不同的軸線：那份是「內容結構」（給答案引擎用的問答節點/定義區塊），這份是
「數學公式本身的字元層級損毀」。

## 根本原因：複製的是「渲染後的畫面」，不是「原始檔」

幾乎所有損毀案例最終都能追到同一個源頭：用 GPT/Claude 的 Canvas（或類似的
即時渲染介面）寫論文時，如果是點「下載 .md」，拿到的是乾淨的原始 LaTeX 原文；
但如果是在渲染畫面上選字複製（因為畫面上公式看起來是對的、直覺會想直接複製），
瀏覽器複製的其實是**渲染引擎處理過的 DOM**，不是原始碼。DOM 裡的結構跟原始
LaTeX 原文長得完全不一樣，複製出來會被「翻譯」成一堆看起來像 markdown、但
語意已經錯亂的字元。

新格式如果能讓 AI 透過 MCP 直接輸出結構化資料（而不是「畫出來給人看，再讓人去
複製畫面」），這整類問題在源頭就不會發生——這是目前唯一「連錯誤都不會產生」的
解法，其他都是損毀後偵測/修復。

## A. Canvas 渲染畫面複製的固定損毀特徵

這是目前 `scripts/normalize_math.py::is_corrupted()` 在抓的訊號，抓到才會觸發
`convert()` 修復：

- `\[` 開啟顯示數學，但配對的收尾從 `\]` 變成單獨一行的裸 `]`（且同一份文件
  裡這種「裸 `]` 收尾」會遠多於正常的 `\]` 收尾）
- 複製過程中的 `<br>` 換行標籤，變成一堆單獨一行、句尾的孤立反斜線 `\`
- `_`（底線）被吃成 `\_`
- `}_{` 被吃成 `}*{`
- inline 數學整個丟掉 `\(...\)` 包裹，變成裸的 `(...)`（跟正常的函數呼叫
  `f(x)` 沒有語法區別，必須用「內容裡有沒有反斜線指令」去猜）
- 公式旁邊的排版標記被誤譯成 `#` 標題或 `----` 分隔線

## B. 三重複製：攤平文字近似 + 真正 LaTeX + 又一次攤平文字近似

比 A 更深層的一種損毀，今天在 lm-000830（程式語言設計的最小勝利構成）修過一個
真實案例。同一段公式被貼了三次，中間沒有任何分隔符號：

```
損毀前：
ROI=38%×$500K(bug cost)2000hours×$100/hour≈0.95\text{ROI} = \frac{38\% \times \$500K \text{(bug cost)}}{2000 \text{hours} \times \$100/\text{hour}} \approx 0.95ROI=2000hours×$100/hour38%×$500K(bug cost)​≈0.95

修好後（只留中間那段真正的 LaTeX）：
\text{ROI} = \frac{38\% \times \$500K \text{(bug cost)}}{2000 \text{hours} \times \$100/\text{hour}} \approx 0.95
```

第一段跟第三段明顯是某種「螢幕閱讀器/無障礙文字」版本的公式攤平結果（第三段
連分子分母的閱讀順序都反過來了，像是照 DOM 視覺排列由下往上讀）。這份文件裡
同樣形狀的公式出現了 29 次，只有這一處因為裡面剛好混了美元金額符號才真的
爆炸——其他 28 處目前只是「渲染成功但畫面上有一大串重複亂碼」，還沒處理，
規模比較大，這次沒有連帶動它。

## C. `$` 的雙重身份：貨幣符號 vs. 數學模式定界符

今天自己修 406 檔案空白問題時踩到的新坑，值得特別記錄。`$` 在這批論文裡同時
被拿來當「數學模式開關」跟「貨幣金額的字面符號」（例如 `\$500K`），兩者只靠
有沒有反斜線轉義區分。我自己寫的空白修正函式一開始沒考慮到「`\$` 是一個不可
分割的跳脫單元」，把它誤判成真正的定界符：

```
損毀前（正確）：$\$D:n$          → 顯示為「$D:n」這個標籤字串
我的 bug 改成：  $ \ $D:n$        → 多插入的空白讓 KaTeX 看到一個真的要求值的 $
```

更麻煩的是：一旦文字裡連續出現兩組「跳脫 `$`」（像 B 案例那樣，一段文字裡有
兩個貨幣金額），錯誤的定界符配對邏輯可能會直接跳過中間整段內容，把兩個完全
不相關的 `$` 錯配在一起，殃及池魚。這類 bug 很難靠肉眼審查抓到，只能靠拿正式
渲染器實際跑一次來驗證。

## D. 定界符方言不一致：`$...$`/`$$...$$` vs 原生 `\[...\]`/`\(...\)`

這個網站目前**同時支援兩套語法**，各自獨立的程式路徑、各自的規則：

- `$`/`$$`（`marked-katex-extension`）：inline 數學要被辨識，左右鄰接字元有
  嚴格規則（見下一條 E）。
- 原生 `\[...\]`/`\(...\)`（`shell/src/lib/md.ts` 自訂 extension）：**必須
  包含至少一個 LaTeX 指令**（`\` 加字母）而且**內部不能有空行**，才會被辨識
  成一個區塊。這條規則是這次 batch 4 才發現的：一個完全不含指令、只有純數字
  跟符號運算的 `\[...\]` 區塊會被原生渲染器完全無視，整段變成字面文字顯示。

同一段語意完全相同的 LaTeX，換一種定界符寫法，能不能正確渲染的結果可能不同。
這是雙路徑架構本身帶來的複雜度，不是內容本身的錯。

## E. 邊界/相鄰字元規則：合法的 LaTeX 也可能因為「站錯位置」不被辨識

就算公式本身完全合法，`$x=5$` 這種 inline 數學要被辨識成數學（而不是純文字），
左右兩側的字元也有規則，而且左右不對稱：

- 左邊：必須是空白，或是段落開頭
- 右邊：必須是空白、`?!.,:？！。，：` 這幾種標點之一，或是段落結尾

但 `*_~`（markdown 自己的粗體/斜體/刪除線標記）是例外——因為 marked 自己的
核心 tokenizer 在踩到這些字元時會先做一次獨立的斷詞，KaTeX extension 才拿到
「重新開始」的機會，所以緊貼著 `*_~` 反而是安全的，不需要補空白。這條規則
完全是 marked 這個特定 parser 的實作細節，不是 LaTeX 或 CommonMark 規範本身
規定的——換一個 markdown 引擎，這條「安全字元表」可能整組不一樣。

## F. 級聯失效：一個小缺陷可以吃掉後面一大段內容

lm-000322 是今天修的案例：文件裡少了一個收尾的 `$`，結果不是「這一個公式壞掉」
而是整個渲染器的定界符配對邏輯,從那個缺口開始,把後面所有內容都當成同一段
還沒結束的數學模式,一路吃到下一個湊巧出現的 `$` 為止——可能是好幾段之後、
完全不相關的另一個公式。畫面上看到的錯誤位置,跟真正缺陷的位置可能隔了一大段
正文。

## G. 機械修復的副作用：修好一種模式,可能弄壞另一種

這類問題比較特別,不是內容本身的損毀,而是「用規則修正錯誤」這個做法自己的
局限。兩個今天/先前踩過的例子:

- 上面 C 案例,我自己的空白修正 regex。
- 更早修「多餘反斜線」時發現：`\\` 在 `aligned`/`cases`/`array` 環境裡是
  正規的換行符號,尤其 `\\[5pt]` 這種「換行 + 額外間距」寫法**兩個反斜線都要
  保留**;但同一份文件裡也有大量「單一多餘反斜線」的複製貼上損毀,兩種形狀
  用同一條「把連續反斜線減半」規則處理,會把合法的 `\\[5pt]` 誤傷成 `\[5pt]`
  （後者在已經開啟的數學區塊裡沒有意義,會直接讓渲染器報錯）。

這類 bug 的本質是:針對「已知損毀特徵」寫的修復規則,沒辦法區分「這個特徵
真的是損毀」還是「這個特徵剛好是某個合法寫法的一部分」,兩者字面上長得一樣。
規則覆蓋的案例越多,兩種合法/非法用法撞在一起的機率也越高。

## H. 字元層級的細碎損毀

沒有系統性規律、只能一個一個處理的損毀,列出來給你知道有這一類存在:

- `D^*`（上標星號）在某個環節被轉成 `D^_`（底線),推測是複製/字型轉換
  過程把星號跟底線搞混,目前找不到更明確的成因。
- 引用文字被 PUA（Private Use Area)字元取代——通常是某個排版軟體用 PUA
  字元做內部標記,複製出來變成不可見或顯示成方框的亂碼。
- `\b`（LaTeX 指令)的反斜線被複製過程吃成真正的 0x08 控制位元組（backspace),
  指令本體斷頭。
- 關係符號 `≠` 直接寫在 `\text{}` 裡面,觸發 KaTeX 內部「`\text{}`是文字模式,
  不該出現需要展開的關係符號」的錯誤。
- 大括號 `{}` 多一個或少一個,兩個方向都有,而且沒辦法只靠數大括號數量機械
  判斷是哪一邊壞的,必須讀懂公式語意才能定位。
- 重複下標,例如同一個識別字元被連續寫了兩次下標(`_i_`、`^*_{...}`這種),
  需要人工判斷兩次下標原本要表達什麼、怎麼合併,不是字元置換能解的。

## 規模感

這幾類問題不是零星個案。今天這一輪(修上一輪遺留 + 順手抓到的新問題)橫跨:
403 個檔案的定界符鄰接空白、1 個結構性缺陷(lm-000322)、46 個既有的 KaTeX
硬錯誤、加上修復過程本身新炸出的 3 個回歸錯誤——全部收斂到 0 之前,中間
經過好幾輪「假設→用真正的渲染器重現→修正→再驗證」。更早之前的批次(見
[Logic Matrix Corpus Engine v0.2 技術白皮書](Logic%20Matrix%20Corpus%20Engine%20v0.2%20技術白皮書.md)
前後的紀錄)也有過一次性抓到 1699 個 KaTeX 錯誤的規模。

## I. 系統性跳脫解碼損毀：`\a\b\f\n\r\t\v` 七個指令的反斜線整批消失

H 案例提過一次「`\b` 的反斜線被吃成 0x08 backspace」，2026-08-12 晚間批次
在一份文件（AI 原生知識展開論系列的「錯誤鄰域與反例空間」）裡看到這其實是
一整類、不是單一案例：C／Python 風格的七個標準單字元跳脫序列
`\a \b \f \n \r \t \v`，只要指令剛好用到這七個字母開頭，反斜線加那個字母
就會被某個上游流程（很可能是 `str.encode().decode('unicode_escape')` 這類
操作，對照 [`feedback-never-unicode-escape-roundtrip`]）解碼成對應的單一
控制字元，指令其餘部分留在原地：

```
\boxed{   →  [BS  0x08]oxed{
\forall   →  [FF  0x0c]orall
\arg\min  →  [BEL 0x07]rg\min
\text{    →  [TAB 0x09]ext{
\rightarrow → [CR  0x0d]ightarrow
\varnothing → [VT  0x0b]arnothing
```

這份文件裡光是這六個控制字元就出現 134 次（`\b`25、`\t`84、`\f`8、`\a`11、
`\r`5、`\v`1），全部是同一種機制造成，修法也統一：把每個控制字元換回對應
的 `\字母`，因為這六個控制字元在正常內容裡不可能合法出現，替換是無歧義的。

**唯一的例外、也是最危險的一種：`\n`（換行)。** 這七個跳脫序列裡只有 `\n`
的目標字元（0x0A 換行）跟檔案本身用來分段落的正常換行完全相同，所以
`\neg`、`\neq`、`\nabla` 這類指令如果中了同一種損毀，會變成「這一行提早結束，
下一行開頭多出 `eg`／`eq`／`abla`」——肉眼看起來完全就是一次普通的段落
換行，KaTeX 也不會報錯（`eg`、`eq` 都是合法的變數名稱組合），只是**畫面上
顯示的意思整段是錯的**（例如「¬P(x)」被靜默地渲染成「eg P(x)」，一個三字母
單字，不是否定號）。這是這次批次唯一一個「自動渲染器 0 錯誤，但語意完全
損毀」的案例類型——只能靠人工逐處讀懂上下文語意去判斷「這裡是不是真的少了
一個換行」，抓一個算一個，沒有機械化判定法。

## J. 整條公式被換成「已經渲染過的畫面文字」，不是 LaTeX 原始碼

跟 B 案例（三重複製）表面相似、但根本原因不同的另一種損毀：2026-08-12 晚間
批次的跨對話系列有一篇（跨對話 Agent 的持續性、喚醒、交接與非連續推理）
整篇文章「零」`$`／`$$`／`\boxed{}`（同系列其他四篇各有幾百個），但論證本身
完整、讀得通——因為所有數學內容不是「消失了」，而是被整段換成畫面渲染後的
Unicode 近似字：下標直接印成同大小的字（`Run_0` 變成 `Run0`，中間補一個
零寬空白字元 U+200B 標記「這裡原來是下標」)、關係運算子直接用對應的 Unicode
符號（`\Rightarrow`→`⇒`、`\to`→`→`)，`\boxed{}` 的框線本身則完全消失，只留
一個私用區（PUA）字元 U+E020 標記「這裡原來有框」。

這跟 A/B 案例（Canvas 畫面複製)是同一個根本原因（複製了渲染後的畫面，不是
原始碼），但損毀的「形狀」不一樣：A/B 是排版標記本身跑位或重複，這裡是
**整個數學語意層被替換成一份人類讀得懂、但機器認不得的近似版本**，而且
零寬空白／PUA 標記恰好精準對應「這裡原來有下標」「這裡原來有框」，所以
只要看到同一份文件裡有系統性分佈的零寬空白／PUA 字元，且該文件完全沒有
`$`/`\[`/`\boxed{}`，就可以判定是這一類、而不是內容真的遺失（跟已經放棄的
「非適應性計算基線」案例——那一種是真的整句話不見了——的關鍵區別：這裡的
每一個公式都能從上下文語意 100% 還原，因為論證本身完整，只是排版方式錯了)。

## 目前應對方式的根本局限

現在的做法是「損毀後偵測 + 特徵比對修復 + 拿正式渲染器重新跑一遍驗證」,這條
路徑本身有兩個結構性問題:

1. **偵測規則是針對「已知」損毀特徵寫的**——新的損毀形狀(像這次的三重複製、
   `\$` 雙重身份)每次都是先炸出一個實際的渲染錯誤,才回頭去讀原始碼、動手
   寫新規則去抓它。沒有辦法窮舉「所有可能的損毀方式」,只能不斷擴充已知清單。
2. **修復規則彼此可能互相踩踏**(見 G)——規則覆蓋的案例越多,不同規則之間
   對同一段字元的解讀衝突機率也跟著上升。

這是這份清單存在的理由:如果新格式能讓 AI 直接透過 MCP 輸出結構化內容(而不是
「渲染給人看,再讓人手動複製畫面」),上面 A、B、J 三類(目前佔比最大的幾類,
J 是 B 的同源變種)在源頭就不會發生;C、D、E 三類則是「定界符本身有沒有
歧義」的設計問題,新格式如果選用不會跟自然語言文字衝突的定界符(而不是
繼續用 `$`這種在日常文字裡本來就有其他含義的符號),也能整類避開。F、G、H、I
比較難單靠格式設計解決,比較接近「輸出前先跑一次真正的驗證,擋掉不合法內容,
而不是事後修」的問題——I 尤其值得注意:`\n` 損毀後跟正常換行完全無法用機器
區分,是這份清單裡唯一一類「渲染器 0 錯誤，但語意仍可能整段錯誤」的案例,
新格式如果從根源避免任何會被跳脫解碼器誤判的字元序列(例如指令不要用單一
反斜線+字母的形式),可以連這類都堵住。
